# 博客后台方案分析与建议

## 背景

当前博客基于 Astro + 自定义 Djot Loader 构建，内容存储为 `.dj` 文件，通过 Git 管理。现需要一个管理后台来替代本地命令行操作（方案 D），实现更便捷的文章发布和修订管理。

## 部署环境

- **管理面板**：Netlify / Vercel（静态部署）
- **代码仓库**：Codeberg（主仓库）← GitHub（中转仓库）← 管理面板
- **使用人数**：1 人
- **当前状态**：方案 D（本地 CLI/GUI 工具）
- **目标状态**：方案 C（Codeberg API + 自建管理面板）

## 为什么选择方案 C

### 排除其他方案的理由

| 方案 | 排除原因 |
|------|----------|
| Decap CMS (Netlify CMS) | 不支持 Djot 格式；无法处理 `_revisions/` 目录结构；复杂 frontmatter 编辑体验差 |
| Headless CMS (Strapi/Directus) | 内容存数据库而非文件；需要运行服务器；与 Git-based 工作流冲突；对个人博客过于重量级 |
| 纯本地工具（方案 D） | 只能在本地使用；无法远程管理；不适合迁移设备 |

### 方案 C 的优势

1. **Djot 原生支持**：可自定义 Djot 编辑器，支持语法高亮和预览
2. **完整目录管理**：可创建目录化文章结构、管理 `_revisions/` 子目录
3. **业务逻辑集成**：理解修订流程、版本编号、frontmatter schema
4. **Git 原生工作流**：内容即代码，所有变更通过 Git commit 追踪
5. **零服务器成本**：纯静态部署，通过 Codeberg API 操作仓库
6. **与现有流程兼容**：无缝对接现有的 `djotLoader.ts` 和构建流程

## 架构设计

### 整体架构

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   管理面板    │────→│  GitHub 中转  │────→│   Codeberg   │────→│  Netlify/Vercel│
│  (Netlify)   │ API │   仓库       │ Sync│   主仓库     │hook │   自动构建    │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
```

### 数据流

```
用户操作管理面板
  ↓
管理面板调用 GitHub API（写入文件到中转仓库）
  ↓
GitHub Webhook / 定时同步 → Codeberg（通过 git mirror）
  ↓
Codeberg Webhook → Netlify/Vercel 触发构建
  ↓
Astro 构建 → 部署静态站点
```

### 为什么需要 GitHub 中转

1. **Netlify/Vercel 集成**：与 GitHub 集成最成熟
2. **API 限制**：Codeberg API 速率限制较严格
3. **CI/CD**：GitHub Actions 可用于同步到 Codeberg
4. **备份**：GitHub 作为镜像备份

## 技术栈

### 管理面板

| 组件 | 选择 | 理由 |
|------|------|------|
| 前端框架 | Svelte / SvelteKit | 轻量、与 Astro 生态兼容、学习曲线低 |
| UI 组件库 | Skeleton / DaisyUI | 轻量、可定制、适合管理界面 |
| Djot 编辑器 | CodeMirror 6 + 自定义 Djot 语言 | 语法高亮、可扩展 |
| API 调用 | Octokit (GitHub REST API) | 官方 SDK、类型完善 |
| 认证 | GitHub OAuth App | 简单、无需额外服务 |
| 部署 | Netlify / Vercel | 静态站点、免费、自动部署 |

### 可选替代方案

| 组件 | 替代选择 | 说明 |
|------|----------|------|
| 前端框架 | Vue / React | 如果更熟悉这些框架 |
| API 调用 | 直接 fetch | 如果不想引入 Octokit |
| 认证 | 个人访问令牌 (PAT) | 更简单，但安全性较低 |

#### 2.2 创建新版本（大修）

点击「创建新版本」后的流程：

```
1. 读取当前 index.dj 内容
2. 将其复制为 _revisions/vN.dj（N = 下一个版本号）
3. 在 index.dj frontmatter 中添加 revisions 条目
4. 用户编辑 index.dj 为新版本内容
5. 提交到 Git
```

**界面**：
```

│ 创建新版本                                          [确认]  │
├─────────────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────────┘
```

## API 设计

### GitHub API 调用

```ts
// 读取文件
GET /repos/{owner}/{repo}/contents/{path}

// 创建/更新文件
PUT /repos/{owner}/{repo}/contents/{path}
{
  message: "更新文章: 标题",
  content: "base64 编码的文件内容",
  sha: "文件的 SHA（更新时需要）"
}

// 删除文件
DELETE /repos/{owner}/{repo}/contents/{path}
{
  message: "删除文件: 路径",
  sha: "文件的 SHA"
}

// 创建目录（通过创建 .gitkeep 文件）
PUT /repos/{owner}/{repo}/contents/{path}/.gitkeep
```

### 管理面板 API 设计

```ts
// 文章相关
GET  /api/posts              // 获取文章列表
GET  /api/posts/:slug        // 获取单篇文章
POST /api/posts              // 创建文章
PUT  /api/posts/:slug        // 更新文章
DELETE /api/posts/:slug      // 删除文章

// 修订相关
GET  /api/posts/:slug/revisions           // 获取修订列表
POST /api/posts/:slug/revisions           // 创建新版本
GET  /api/posts/:slug/revisions/:version  // 获取旧版本内容

// 媒体相关
GET  /api/media              // 获取媒体列表
POST /api/media              // 上传媒体
DELETE /api/media/:filename  // 删除媒体
```

## 安全考虑

1. **认证**：使用 GitHub OAuth，不存储密码
2. **权限**：仅授予 `repo` 权限（读写仓库）
3. **Token 存储**：使用环境变量，不提交到代码仓库
4. **HTTPS**：所有 API 调用使用 HTTPS
5. **CORS**：配置允许的域名

## 风险和缓解

| 风险 | 缓解措施 |
|------|----------|
| GitHub API 速率限制 | 使用条件请求、缓存；单用户使用 unlikely 超限 |
| Codeberg 同步失败 | 定时检查、失败通知、手动同步备选 |
| Djot 编辑器复杂度 | 可先用纯文本编辑器，后续添加语法高亮 |
| 部署配置错误 | 使用环境变量、CI/CD 自动化 |

## 总结

方案 C（Codeberg API + 自建管理面板）是当前场景的最佳选择：

- ✅ 完全兼容现有 Djot 工作流
- ✅ 支持复杂的目录结构和修订管理
- ✅ 零成本运行
- ✅ 与现有 Git-based 工作流无缝集成
- ✅ 单用户使用，复杂度可控

建议按阶段逐步实现，先完成核心的文章管理功能，再扩展修订和媒体管理。
